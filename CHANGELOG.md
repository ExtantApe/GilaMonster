# Changelog

## Unreleased

- **A server is called by its server message (K824).** The Overview used to say the folder's name, as in "pebble-survival is up". It now uses the server message players see in their server list, so a server whose motd is a green, bold "Made-up Realms" reads "Made-up Realms is up". GilaMonster takes the first line of the motd and removes its colour and format codes (§ and the character after it, the §x hex colours, and the & codes the Configs page already treats as codes). When the message is empty, only codes, longer than 40 characters or the default "A Minecraft Server", the folder's name is shown as before. Only the motd line of `server.properties` is read for this.
- **Your own name for a server wins, and Reset takes it back (K824).** **Rename…** in the Overview's More menu opens the rename sheet with the current name filled in. A name you type there is yours and is kept in GilaMonster's settings for that server, never in `server.properties`. **Reset to Server Message** drops it, so the server message names the server again. A line in the sheet says which of the two is in use, and VoiceOver reads it as the field's hint and hears it when Reset is pressed. A name you gave a server before this version counts as yours. Renaming still renames the server's backup folder and the name sessions use, as it did before; Reset leaves both alone.
- **The same name everywhere, with the folder still in sight (K824).** The headline and what VoiceOver reads for it, the window title, the server switcher, the menu bar, the quit question, page subtitles and notifications all use that name. When it differs from the folder's name, a small muted line under the headline reads "Folder: pebble-survival" and the window's subtitle starts with the folder. Show in Finder and Copy Folder Path are unchanged. Sessions still name a server by its stored name, which is the folder's name until you rename the server.
- **The name under the server's icon can be read (K824).** It used to be cut in the middle of a word. It now takes up to two lines and breaks between words, so "Riverbend Mountain" shows whole. A longer name keeps the whole words that fit and ends in an ellipsis, and a single very long word is cut once, at its end. The tooltip and the VoiceOver label always carry the whole name, with the folder when it differs. Owner, 2026-11-26: "The server name should show in the dropdown though and below it so you don't have to guess."
- **Every row in the server switcher shows its folder (K824).** Each row has the server's name and state, with the folder's name beneath it as the menu item's small grey second line, so two servers with the same server message can be told apart. VoiceOver reads a row as "Made-up Realms, folder survival, Running".
- `scripts/snapshot-fixtures.sh` takes `MOTD=` to give the first made-up server a server message, `RENAME=` to add an owner's name on top, and `TWIN=1` to add a second server with the same message. The snapshot also draws the switcher's rows as `dialog-switcher-rows.png`, as plain views with the menu's words.
- Tested: 102 new checks with made-up names and a made-up `server.properties` that also holds made-up passwords: stripping codes, reading only the motd line, a rename beating the message and surviving a relaunch, Reset, a label from before this version, two servers sharing a message, and the two-line name under the icon. With the app's sources put back as they were, the nine checks that read them failed; the rest use functions this change added. The full check suite from a scratch build passes (4383 checks). The Overview, the rename sheet and the switcher's rows were looked at in off-screen pictures, Bold light and dark, for a coded message, a long message, a long name, two servers sharing a message and a rename. Not tried: the real switcher menu (its second line is drawn by macOS and the off-screen pictures can't open a menu), the window title and subtitle, the menu bar, a real notification, and the rename sheet with a keyboard or VoiceOver. Nothing was run on a real server.
- **Backup ages say whose backup they mean (K823).** The Overview read "backed up 23 hours ago" on a server that another tool was also backing up every 20 minutes, into a folder GilaMonster was never given. The age was right for GilaMonster's own backups, and it read as if the server had gone a day without one. GilaMonster counts the backups it made, in the server's own backup folder and in each folder added under Storage, in order. The Overview's line now reads "GilaMonster backup 23 hours ago", or "no GilaMonster backup yet". The Backups card on Overview labels the age **GilaMonster's latest** and says under it that backups made by other tools aren't counted. The Backups page says the same under Saved backups.
- **Needs you says "No GilaMonster backup yet" (K823).** It used to say there was nothing to restore if something went wrong, which GilaMonster can't know when another tool keeps backups. It now says GilaMonster has made no backup of this server and can't see backups other tools make. Back Up Now is still its button. There is no warning for an old backup, so nothing else needed changing there.
- **Each storage folder shows its newest backup (K823).** On the Backups page, every row under Storage, in order has a line such as "Newest GilaMonster backup here: 4 days ago." or "No GilaMonster backup here yet." A drive that isn't connected gets no line, because what's on it is unknown until it's back.
- **Other tools' backups are still left out, on purpose (K823).** GilaMonster has no way to be pointed at a folder that another tool fills. Every folder it can be given (Saved to, Storage, in order, Also copy to) is one it writes its own backups into, and it reads only archives with its own record beside them. Adding the other tool's folder to Storage would send GilaMonster's backups there and still wouldn't count the other tool's. Watching such a folder would be a new feature and isn't in this change.
- `scripts/snapshot-fixtures.sh` now gives its first server made-up backups: one from 23 hours ago, and an added storage folder with one from 4 days ago. `BACKUPS=none` leaves them out, and `HEIGHT=` draws taller pictures. The first pictures showed that the app's weekly backup drill also runs during a snapshot once a whole-folder backup exists: it tried the placeholder archive, failed to unpack it and raised an issue. The made-up server now has the drill turned off. The app itself still doesn't hold the drill back in a snapshot.
- Tested: 31 new checks in `backupSeenChecks`, with a made-up server, its backup folder, an added storage folder and another tool's newer dated folders placed beside and inside both. The 17 checks that could run against the old code failed there (13 new ones and 4 older ones whose expected words changed). The full check suite from a scratch build passes after the rebase onto K824 (4414 checks, none failing). Overview and Backups were drawn off screen in Bold, light and dark, with the made-up backups and with none, and looked over. Not tested: the app on screen, VoiceOver's speech, a real external drive being unplugged, and the owner's real servers and backup folders. The other tool's script wasn't found in a repo or a scripts folder, so it wasn't read; its folder was only listed by name.

- **A backup drill's server no longer outlives GilaMonster (K813).** A drill boots a throwaway copy of a backup on its own port. When GilaMonster was told to quit by a signal during a drill, it stopped the listed servers and left the drill's Java running with nobody to stop it. The copy was never on the list of servers to stop, so an ordinary Quit with no server running left it too. Now every way out (Quit, a shutdown or log out, SIGTERM, SIGHUP, SIGINT) stops the drill's Java and removes its copy. Nothing is recorded about the backup when a drill ends that way, since it says nothing about the backup.
- **A drill copy left behind is cleared at the next launch (K813).** A force quit, a crash or a power cut can't be caught. So each drill copy now gets a mark beside it when it's made (`<name>.gilamonster-drill`), and at launch GilaMonster looks where drills unpack, stops the Java in any marked copy that's still running, and removes the copy. It removes only real folders with a drill's name and that mark. A folder without a mark, a link, and every other test copy are left alone, and nothing is looked at while another GilaMonster is running. A drill copy made by an older version has no mark and stays until you remove it.
- **A process is signalled only when it is that drill's Java.** The copy's own `server.pid` has to name it, it has to be running, its program has to be Java, and its working folder has to be that drill copy. A number that now belongs to another program, or to your real server (a copy unpacked from a backup can carry the real server's pid file), is never signalled. If a drill's Java won't stop, its copy is left as it is and the log says so.
- A finished drill used to delete the whole `.test-copies` folder beside the backup. It now removes its own copy, and that folder only when it's empty.
- macOS has no setting that ends a child process with its parent, and Java doesn't watch a pipe for it, so the launch sweep is what covers a force quit.
- Tested: new checks, in `gilamonster-check` and on their own with `--drills`. With the stand-in jar: a second copy of the check program runs a real drill and is sent SIGTERM, then SIGHUP, and each time the drill's Java is gone, the copy and mark are removed, and the server and its backup are untouched; a Java left running in a marked copy is stopped by the sweep and its copy removed; a marked copy whose stale pid file names another server's running Java is removed and that Java keeps running; an unmarked folder is left alone. With the stop on the way out and the sweep switched off, 23 of these failed, among them the drill's Java still running after each signal. The full check suite from a scratch build, after rebasing onto K824: 4479 passing, none failing. Not tested: the app itself being signalled or quit during a drill (the app layer isn't in the check harness and the owner's app is running, so the app's calls are read from its source); a drill's Java that ignores SIGTERM and has to be forced; real Paper in a drill; a tar still unpacking when GilaMonster is force quit.
- **A running server no longer shows as unreachable in Connections (K822).** The Overview could say "Friends may not be able to connect" and mark the game tunnel Not ready while the server was up and listening. GilaMonster decided by sending the game's status ping straight to the server. A server with Paper's `proxy-protocol` turned on drops any connection that doesn't begin with the PROXY header, so the ping got nothing while players coming through the tunnel got in. A server with `enable-status` off behaved the same way. The check now opens a plain connection first, which sends nothing, and that alone decides whether something is listening. The ping is sent only to a server that would answer one.
- **A check that can't decide says so (K822).** A timeout or any other error now reads "Couldn't check 127.0.0.1:25565" with the reason, and a closed port while the server is still starting reads as still starting. Both are shown as unknown and stay out of Needs you. Only a refused connection on a running server is Not ready. A start or stop clears the last answer in Needs you until the new check has run.
- Tested: 33 new checks, most on real sockets with stand-in servers on 127.0.0.1 bound over IPv4 only: one that drops the ping, one that answers it, one started late on the same port, one that never accepts (a timeout) and a closed port (refused). Run against the old check, 17 of them failed. Not tested: the app on screen, a real Paper server with `proxy-protocol` on (the owner's running server was only looked at: its port accepts a plain connection that sends nothing), and the clearing on start and stop, which is one line read in the source.

- **The Lab keeps a plugin with the plugins it requires (K804).** GilaMonster now reads what a `paper-plugin.yml` requires, under `dependencies`. It used to read only the `depend` list of a `plugin.yml`, so a Paper plugin could be tried in an earlier group than a plugin it requires and be marked failed. A plugin and everything it requires, however long the chain, now run in one group, the earliest any of them was in. Optional plugins don't move anything. The Plugins page and the upgrade check use the same reading, so a Paper plugin whose required plugin is missing now says so there too.
- **A plugin that can't run in the Lab is skipped (K804).** When a plugin requires one the Lab leaves out, one that isn't installed or one that's turned off, the Lab doesn't install it. Its row reads, for example, "Skipped: needs MadeUpMaps (left out of the lab)." beside the skipped mark, which VoiceOver reads as skipped, and it doesn't turn the light red. A plugin that requires a skipped plugin is skipped too. Inside a group, when a plugin doesn't load and another one only required it, the first stays failed and the second is skipped. A group where nothing ran gets a **Skipped** badge, and the line under Plugins load counts the skipped plugins. All five checks on the Lab page follow this.
- **Each group keeps its restart log (K804).** The Lab's console from stopping to the bot player rejoining is kept with that group's result, up to its newest 400 lines, and shown under the group as **Restart log** with **Copy Log**. It used to go with the lab when the run ended. The lab has only its own bot players and listens only on this Mac, so the log has no real player or address in it. At Your plugin settings it also has whatever the plugins print under your real settings, and it stays in the lab's results file on this Mac. A failed "A change survives a restart" now says which step failed: the block couldn't be placed, the server didn't start again, the player couldn't get back in (with what the server told it, when it said anything), or the block was gone.
- Tested: 56 new checks with made-up jars that hold only a descriptor (a chain of three, two plugins that require each other, an optional plugin, a missing required plugin reported as skipped, and two groups each keeping their own log). The ten that could run against the old code failed there. The full check suite from a scratch build passes (4141 checks). One real run on a throwaway Paper 26.3 lab on this Mac, with four made-up jars: two plugins were skipped with their reasons, the lab was deleted, and the group kept a 101-line restart log that ends with the player rejoining. The Lab page was drawn off screen in the bold theme, light and dark, with a skipped plugin and two restart logs. Not tested: the app on screen, VoiceOver's speech, Copy Log as a click, the other four checks with a skipped plugin on a real lab, and a real server's plugins. The cause of the two restart failures in the 2026-11-26 run wasn't found, because that run kept no log.
- **Use made-up names in code comments and checks (K827).** A real server's name was in one code comment, in the rename checks, in two lines of the plan and as a pack id in the overlap experiment. The comment, the checks and the plan now use Riverbend Mountain, with the same four folder forms, the camel-case form and the `screen -S` script line. The overlap experiment now takes the pack's id and title from the first zip in its `given` folder. Older commits keep the old text. Tested: the check suite from a scratch build up to the end of the rename sections passes, and the overlap experiment was run with one made-up zip. Not tested: the rest of the suite, which this change doesn't touch, and the overlap experiment with a real pack.

## 0.6.2 (2026-11-26)

- **Installing:** quitting GilaMonster stops every server it runs. With servers running, Quit asks first; Keep Running is the default and cancels the quit. So install at a quiet time: quit with Stop and Quit, replace GilaMonster in Applications, open it, and start your servers again. GilaMonster isn't signed, so on first open macOS asks again for Keychain access. This version shows a banner while it waits; look for the macOS password window and click Always Allow. If macOS warns about the app: System Settings > Privacy & Security, Open Anyway, then Open. Or run `xattr -dr com.apple.quarantine "/Applications/GilaMonster.app"`.

- **The Invites demo builds again (K811).** `gilamonster-check --demo-invites`, which the owner's Allowlist and Invites check uses, stopped with a 404 because it asked for Sheriff 0.4.1 and WelcomeWagon 0.3.0 under their new names, and those releases only carry the old-name jars. It now pins Sheriff 0.5.1 and WelcomeWagon 0.7.0, with the sha256 GitHub publishes for each. Tested by running the demo with these pins and walking the Allowlist and Invites screens in a test copy.
- **A Keychain wait now shows in the app (K809).** GilaMonster isn't signed, so after an update macOS asks again before handing over what GilaMonster saved in the Keychain. On 2026-11-26 that password window sat behind other windows for about 40 minutes. Nothing in the app said so, and session access didn't answer. Now, once a Keychain call has waited 2 seconds, a banner at the top of the window says: "GilaMonster is waiting for you to allow Keychain access. Look for a macOS password window. It may be behind other windows." It also names what is waiting: session access, the Advisor's key, or both. The banner goes when you answer. VoiceOver announces it with where to look, and reads the banner as one item. If macOS already lets GilaMonster send notifications and Mac alerts are on, one notification is posted too, and removed when the wait ends. Nobody is asked for notification permission for this.
- **Sessions are told about the wait.** The session socket now opens before the token is read. Until the token is in hand, every request is refused with "GilaMonster is waiting for Keychain access on the Mac", and each refusal is in the call log. Nothing is allowed without the token.
- **A no at the password window is kept.** GilaMonster used to answer a refused read by making a new token and listening anyway. Now session access stays off, a banner says sessions can't check status or run commands, and **Try Keychain Again** asks macOS once more. While macOS is asking, the same banner stays and says so, its button is gray, and the keyboard focus moves to Dismiss. A new token is made only when there is none.
- **VoiceOver hears how a Keychain wait ended.** "Keychain access allowed. Session access is on." or "Keychain access wasn't allowed. Session access is off.", every time, a second no in a row included. An ordinary launch, where nothing waits, says nothing.
- **Button outlines inside callouts are held to the contrast checks.** The plain and main button outlines and the focus ring are now checked on all four callout washes. One pair was short: the plain button's outline on the danger wash in light with Increase Contrast, at 4.49:1 against a 4.5:1 minimum. That wash is one shade lighter (`#E9D8D0` to `#EBDBD2`, by tinting 9% where it was 10%). No other color changed.
- `scripts/snapshot-fixtures.sh` takes `KEYCHAIN=wait` or `KEYCHAIN=denied` to draw a made-up Keychain banner on every page, `PAGES=` to draw only some pages, and `SCRATCH=` to build outside `.build`. The snapshot now draws pages at the real window's minimum size (1120 by 640).
- **A banner with a second line no longer pushes the page up.** The first snapshots of the Keychain banners showed the page shifted up out of view, further the longer the banner's second line was. The two Keychain banners now lay that line out in a way the banner row sizes correctly. It was seen only in off-screen pictures. The other banners with a second line in that row (a server running outside GilaMonster, a finished test copy) are unchanged and still need a look.
- **Allow Keychain Access on the Advisor page no longer freezes the window.** That press waited for macOS on the main thread. It now waits in the background, with the same banner.
- Tested: the full check suite from a scratch build (4226 passing, none failing), with new checks that use a stand-in Keychain that blocks until released. They cover the banner turning on after the threshold and off on return, the read staying off the main thread, the refusal a session gets during the wait, the denied case, a failed read, Try Keychain Again, turning session access off or off and on during the wait, the spoken lines, and the new color pairs. Both banners were drawn off screen on Overview, Console and the welcome screen in Bold light, Bold dark and Quiet light, and looked over for clipping and wrapping. Not tested: a real macOS password window (none was triggered on purpose), the real window on screen, VoiceOver's speech, where the focus lands after a retry, and the notification as macOS shows it.

- **The Lab's switches are drawn by GilaMonster (K801).** The check rows used the system switch, which was seen half on: a teal track with the knob in the middle. The new switch has its knob at one end or the other. During a run it keeps its end, turns gray with a dashed outline and shows a lock, and VoiceOver reads "On, locked while a run is going". - **Disabled buttons are readable (K801).** A disabled button was the enabled one at half strength, which put Run Checks between 2.2:1 and 2.6:1. It now has muted words on the raised fill with a dashed outline: 6.9:1 in light and 7.0:1 in dark, in Bold and Quiet. This applies to every disabled themed button in the app.
- **Each server keeps a record of what stopped it (K798).** `.gilamonster/stops.jsonl` in the server's folder gets a line when a stop is asked for and a line when the server exits: the time, what asked, and the exit code. The sources are the Stop and Restart buttons (with which one), the Server menu, its keyboard shortcut, the menu bar, a session with the name it gave, quitting GilaMonster, the Mac shutting down or restarting, logging out, a quit signal, the Lab, Force Stop, stop typed in the console, and GilaMonster's own reasons such as a planned restart or a restore. When GilaMonster didn't ask, the line says the server stopped on its own or from outside. The file is cut back to its newest 400 lines once it passes 256 KB. It holds no player names, chat or addresses. Overview shows the last stop under the fact line while the server is down, the console says what stopped it, and History's stop entry does too.
- **Leftover backup clones are removed at launch (K799).** A backup that was cut short left its clone in `GilaMonster/backup-clones` beside the servers. Each launch now removes only clones GilaMonster marked as its own when it made them: a plain `<name>.gilamonster-clone` file beside each one, written from 0.6.1 on. Clones left by older versions have no mark and stay where they are for you to decide on. It does nothing while a backup or another copy of GilaMonster is running, follows no links, leaves everything else in that folder alone, and logs what it removed.
- Tested: off-screen pictures of the Lab and the Allow prompt in light and dark, and the full check suite from a scratch build (3917 of 3918 passing, with new checks for each fix, with checks for each fix). The one failure is the gilamonster-mcp check, whose binary a scratch build can't start; CI runs it. The stop file was checked with a real Java process on the stand-in jar: stops from a button, a session, the console, a restart and a signal from outside. The clone sweep was checked on made-up folders with links pointing outside them. The Allow prompt's layout was measured in a standalone SwiftUI copy of the row at 13, 20 and 28 pt. Not tested: anything on screen (the app wasn't launched), VoiceOver, the real Allow window at a larger macOS text size, the menu and shortcut being told apart by a real key press, a real quit or Mac shutdown, and the sweep at a real launch. ## 0.2.0

Tested against real Paper 26.x servers started for the tests, with made-up players, and with the real plugins named
below. Not yet tested by anyone running it on a server people play on. The new screens haven't been checked with a
keyboard and VoiceOver yet. Plugin commands and the Advisor are off until you turn them on.

**Opening it:** GilaMonster is unsigned, so macOS blocks the first launch. Allow it one of two ways:

- **System Settings:** try to open the app once, then go to System Settings > Privacy & Security, scroll down, click
  **Open Anyway**, and click **Open** when the warning comes back. Apple says to do this only for an app you trust.
- **Terminal:** `xattr -dr com.apple.quarantine "/Applications/GilaMonster.app"`

Players and sign-in:

- Add someone to the allowlist before they've ever joined, with their LuckPerms groups. Groups you haven't ticked are
  never offered, and you can mark pairs of groups that shouldn't be combined.
- With Usher installed, approving someone goes through Usher's profiles and its questions, and never around it. People
  the whitelist turned away are listed. Needs Plugin commands, which is off by default.
- With Latchkey, make six-character invites for one Minecraft name with Usher profiles, see the code once, and list or
  revoke them. With Latchkey 0.3, the card shows whether its lobby is on, and each player's sheet can sign them out of
  the web pages everywhere.
- A page listing your plugins for people on the server, and BlueMap's web map behind the same sign-in. Players sign
  in with `/signin` in the game, through Latchkey. Both are off by default.

Resource packs:

- See what each pack contributes, serve packs from this Mac with their own address per build, and serve an exact pack
  file unchanged. Serving comes back when the app opens.
- Leave out any song a pack lists in its `songs.json`, so Minecraft's own track plays.

Upgrades and the rest:

- Before an upgrade, check plugins with Preflight's own tool on a copy, and offer to switch off ones that won't start.
- Pick the server icon from a folder of choices in `server-icons/`.
- The Advisor, an optional page that asks Claude Code for suggestions about a server, using your own Claude account.
  It's off until you turn it on in Settings, each server has to be shared, and the first check asks before sending.
  Only recognised log lines, stack traces and a fixed list of settings are sent, with players and addresses replaced
  by code names. The list of who each code name stands for is sealed with a key in your Keychain. macOS asks for
  that key once, and again after each update until GilaMonster is signed. See `docs/ADVISOR-SECURITY.md`. Tested with
  made-up servers. It hasn't been run on a real server yet.

## 0.1.0

The first release. Tested against real Paper servers started for the tests, with made-up data. Not yet tested by
anyone running it on a server people play on.

- Runs a Minecraft Java server from a Mac app: console, CPU and memory, restart after a crash with a limit, and
  keeps the Mac awake while running.
- Finds the server software, version, memory and flags of an existing server, and keeps everything it adds in
  `.gilamonster/`.
- Keeps Paper, Folia, Purpur, Vanilla or your own jar current, with hashes checked.
- Updates plugins from Modrinth, Hangar, SpigotMC, GitHub Releases, Jenkins or any web address, skipping
  releases tagged for another Minecraft version.
- Settings forms generated from `server.properties`, Bukkit, Spigot, Paper and each plugin's config.
- The Lab, a practice server with bot players for rehearsing an upgrade before doing it for real.
- Resource pack recipes: version, rank, build and share packs.
- A plugin links page listing each plugin, its version and where to read about it. It replaces the wiki.
